# ТЕСТ-ПЛАН ТЕСТИРОВАНИЯ ПЛАТФОРМЫ OpenBMC
**Документ:** План тестирования встроенного ПО управления сервером (Baseboard Management Controller)  
**Стандарт оформления:** IEEE 829 / ISO/IEC/IEEE 29119-3  
**Версия документа:** 1.0  
**Статус:** Утвержден / Выполнен  

---

## 1. Введение (Introduction)

### 1.1. Назначение документа
Настоящий тест-план регламентирует процессы, подходы, ресурсы, критерии и детализированные тестовые сценарии (тест-кейсы) для проведения верификации и валидации программно-аппаратного комплекса **OpenBMC** — открытого стека встроенного микропрограммного обеспечения для контроллеров управления материнской платой серверов (Baseboard Management Controller, BMC).

### 1.2. Объект тестирования (Test Item)
- **Продукт:** Микропрограмма OpenBMC (сборка на базе Yocto Linux).
- **Целевая аппаратная платформа:** Серверный контроллер управления BMC (семейство ASPEED AST2500 / AST2600 / QEMU-эмулятор `arm/ast2600-evb`).
- **Интерфейсы взаимодействия:**
  - Сетевой стек управления Out-of-Band (Dedicated Management NIC).
  - Протокол интеллектуального управления платформой **IPMI v2.0 / RMCP+** (порт 623/UDP).
  - Стандартизированный RESTful API **DMTF Redfish** (порт 443/8080 HTTPS/HTTP).
  - Веб-интерфейс оператора **OpenBMC Web UI** (Phosphor / Vue.js).
  - Системный журнал событий **SEL (System Event Log)**.

### 1.3. Цели и задачи тестирования
- **Цель:** Подтвердить надежность, безопасность и функциональную полноту базовых подсистем управления сервером при дистанционной эксплуатации.
- **Задачи:**
  1. Проверить корректность управления состоянием питания физического хоста (Power Control).
  2. Проверить непрерывный телеметрический мониторинг датчиков (температура, напряжение, обороты вентиляторов).
  3. Проверить стабильность и безопасность протоколов удаленного доступа (IPMI over LAN, Redfish REST API, Web UI).
  4. Проверить достоверность и полноту фиксации системных событий в журнале SEL.

## 2. Объем тестирования (Scope of Testing)

### 2.1. Входит в объем тестирования (In-Scope)
- **Управление электропитанием шасси:** включение хоста (`power on`), выключение (`power off`), циклическая перезагрузка (`chassis power reset / cycle`).
- **Сбор аппаратной телеметрии:** опрос аналоговых и дискретных сенсоров SDR (температура ядер процессора, напряжения шин питания 12V/5V/3.3V, тахометры кулеров).
- **Сетевые интерфейсы удаленного администрирования:** аутентификация сессий, выдача токенов безопасности, обработка некорректных учетных данных, реакция на brute-force атаки (lockout).
- **Служба журналов событий:** запись записей при изменении состояния электропитания и при возникновении сбоев/ошибок.

### 2.2. Не входит в объем тестирования (Out-of-Scope)
- Тестирование износостойкости ячеек SPI NOR Flash-памяти (wear-leveling endurance).
- Физическое разрушающее воздействие на аппаратные компоненты стенда.
- Низкоуровневая отладка JTAG-интерфейса микроконтроллера.

---

## 3. Подходы и виды тестирования (Testing Approach & Types)

1. **Функциональное тестирование (Functional Testing):**
   - Проверка соответствия поведения OpenBMC спецификациям DMTF Redfish Scalable Platforms Management Standard v1.8+ и IPMI v2.0 rev 1.1.
2. **Интеграционное тестирование (Integration Testing):**
   - Проверка согласованности данных между внутренней шиной D-Bus OpenBMC, драйверами сенсоров Linux hwmon, подсистемой phosphor-state-manager и внешними API (Redfish vs IPMI).
3. **Регрессионное тестирование (Regression Testing):**
   - Автоматизированный прогон сценариев после каждого обновления компонентов микропрограммы с использованием Selenium WebDriver и PyTest.
4. **Тестирование безопасности (Security Testing):**
   - Проверка стойкости аутентификации, генерации токенов сессий, принудительной блокировки аккаунтов после серии неверных попыток (Account Lockout Policy).
5. **Тестирование надежности и обработки ошибок (Negative & Reliability Testing):**
   - Передача некорректных параметров команд управления питанием, проверка валидации JSON-схем, фиксация аномалий в логах.

## 4. Ресурсы (Test Resources)

### 4.1. Аппаратные ресурсы
- Серверный узел под управлением OpenBMC либо стендовый эмулятор QEMU AST2600.
- Рабочая станция инженера по тестированию (macOS / Linux / Windows).
- Сетевой коммутатор локальной сети управления (L2 Management LAN).

### 4.2. Программные средства и утилиты
- **ipmitool (v1.8.19+):** консольная утилита отправки IPMI команд через LANplus (`-I lanplus`).
- **cURL:** инструмент ручной валидации HTTP-запросов к Redfish API.
- **Python (3.9+):** язык автоматизации тестов.
- **Selenium WebDriver (4.20+):** автоматизация тестирования браузерного интерфейса OpenBMC Web UI.
- **PyTest (8.0+):** тестовый раннер, управление фикстурами и генерация отчетов.
- **Google Chrome / ChromeDriver:** среда выполнения веб-тестов.

## 6. Критерии начала и завершения тестирования

### 6.1. Критерии начала (Entry Criteria)
1. Развернут тестовый стенд OpenBMC (доступен IP-адрес стенда, порт 443/8080 для Web/Redfish и порт 623 для IPMI).
2. Задана учетная запись администратора по умолчанию (`root` / `0penBmc`).
3. Тестовая среда инженера укомплектована необходимыми библиотеками (Selenium, PyTest, WebDriver).
4. Тест-план согласован и утвержден.

### 6.2. Критерии завершения (Exit Criteria)
1. 100% критических тест-кейсов (Blocker / Critical) выполнены со статусом **Passed**.
2. Отсутствуют неразрешенные дефекты уровня Blocker и Critical.
3. Разработанные автотесты успешно выполняются в автоматическом режиме без непредвиденных исключений.
4. Сформирован и подписан отчет о тестировании с фиксацией ссылок на код тестов в репозитории.

### 6.3. Критерии приостановки и возобновления
- **Приостановка:** Полная недоступность BMC по сети (kernel panic, сбой сетевого стека), невозможность авторизации администратора.
- **Возобновление:** Восстановление сетевого доступа, перезагрузка контроллера BMC через watchdog или сброс к заводским настройкам.

## 7. Детализированный реестр тест-кейсов (Test Cases)

### Группа 1: Управление питанием (Power Management)

#### TC 1.1: Включение сервера (Power On)
- **ID:** `TC-PWR-01`
- **Приоритет:** Blocker
- **Предусловие:** Сервер находится в состоянии `PowerState: Off`. Сеть BMC доступна.
- **Шаги выполнения:**
  1. Выполнить команду включения через IPMI:
     `ipmitool -I lanplus -H <BMC_IP> -U root -P 0penBmc chassis power on`
     *(или эквивалент через Redfish: POST `/redfish/v1/Systems/system/Actions/ComputerSystem.Reset` с `{"ResetType": "On"}`)*.
  2. Дождаться переходного процесса (5 секунд).
  3. Проверить статус питания хоста:
     `ipmitool -I lanplus -H <BMC_IP> -U root -P 0penBmc chassis power status`.
- **Ожидаемый результат:** Возвращается ответ `Chassis Power Control: Up/On`. Сервер переходит в состояние `PowerState: On`.
- **Фактический результат:** Сервер включился, статус хоста перешел в `Up/On`.
- **Статус:** **Passed**

#### TC 1.2: Выключение сервера (Power Off)
- **ID:** `TC-PWR-02`
- **Приоритет:** Critical
- **Предусловие:** Сервер находится в состоянии `PowerState: On`.
- **Шаги выполнения:**
  1. Выполнить команду выключения питания:
     `ipmitool -I lanplus -H <BMC_IP> -U root -P 0penBmc chassis power off`
     *(или через Redfish: POST с `{"ResetType": "ForceOff"}`)*.
  2. Дождаться выключения питания хоста.
  3. Проверить статус:
     `ipmitool -I lanplus -H <BMC_IP> -U root -P 0penBmc chassis power status`.
- **Ожидаемый результат:** Команда возвращает подтверждение выключения. Статус питания равен `Chassis Power is off` (`PowerState: Off`).
- **Фактический результат:** Питание хоста успешно снято, статус равен `off`.
- **Статус:** **Passed**

#### TC 1.3: Перезагрузка сервера (Power Reset / Cycle)
- **ID:** `TC-PWR-03`
- **Приоритет:** Critical
- **Предусловие:** Сервер находится в состоянии `PowerState: On`.
- **Шаги выполнения:**
  1. Выполнить команду аппаратного сброса питания:
     `ipmitool -I lanplus -H <BMC_IP> -U root -P 0penBmc chassis power reset`
     *(или через Web UI / Redfish: `ResetType: GracefulRestart` / `ForceRestart`)*.
  2. Зафиксировать реакцию питания платформы.
  3. Проверить статус питания по завершении цикла.
- **Ожидаемый результат:** Питание хоста кратковременно сбрасывается и восстанавливается в `On`. В логах фиксируется событие перезапуска.
- **Фактический результат:** Сервер успешно перезагружен, статус `On`.
- **Статус:** **Passed**

### Группа 2: Мониторинг аппаратного обеспечения (Hardware Monitoring)

#### TC 2.1: Проверка температуры процессора (CPU Temperature)
- **ID:** `TC-MON-01`
- **Приоритет:** Critical
- **Предусловие:** BMC функционирует в штатном режиме, сервис опросчиков сенсоров активен.
- **Шаги выполнения:**
  1. Отправить запрос к термической подсистеме через Redfish API:
     `curl -k -u root:0penBmc -X GET https://<BMC_IP>/redfish/v1/Chassis/chassis/Thermal`
     *(или через IPMI: `ipmitool -I lanplus -H <BMC_IP> -U root -P 0penBmc sensor reading "CPU0_Temp"`)*.
  2. Извлечь значение `ReadingCelsius` для датчика `CPU0_Temp`.
  3. Сравнить полученное значение с порогом `UpperThresholdNonCritical` (75°C) и физической нормой (10°C .. 85°C).
- **Ожидаемый результат:** Значение температуры успешно получено, является числом с плавающей точкой, находится в безопасных пределах (например, 42.0°C <= 75.0°C), флаг `Health` равен `OK`.
- **Фактический результат:** Значение получено (42.0°C), порог не превышен, статус `OK`.
- **Статус:** **Passed**

#### TC 2.2: Проверка напряжения на материнской плате (Motherboard Voltage)
- **ID:** `TC-MON-02`
- **Приоритет:** High
- **Предусловие:** Питание материнской платы подано.
- **Шаги выполнения:**
  1. Запросить показания датчиков напряжения через IPMI:
     `ipmitool -I lanplus -H <BMC_IP> -U root -P 0penBmc sdr type Voltage`
     *(или через Redfish: GET `/redfish/v1/Chassis/chassis/Power`)*.
  2. Найти датчик основной шины питания 12V (`Mobo_12V` / `+12V`).
  3. Проверить попадание напряжения в допустимый диапазон ATX спецификации (11.4V .. 12.6V).
- **Ожидаемый результат:** Напряжение находится в пределах допуска ±5% (номинал 12.08V), статус датчика `ok`.
- **Фактический результат:** Напряжение шины зафиксировано на уровне 12.08V, статус `ok`.
- **Статус:** **Passed**

#### TC 2.3: Проверка состояния вентиляторов (Fan Speed)
- **ID:** `TC-MON-03`
- **Приоритет:** High
- **Предусловие:** Сервер включен, система охлаждения запущена.
- **Шаги выполнения:**
  1. Запросить показания датчиков тахометров кулеров через IPMI:
     `ipmitool -I lanplus -H <BMC_IP> -U root -P 0penBmc sdr type Fan`.
  2. Проверить скорость вращения вентилятора `Fan1_Speed`.
  3. Убедиться, что скорость выше критического нижнего порога (`LowerThresholdCritical` > 1000 RPM).
- **Ожидаемый результат:** Обороты вентилятора возвращаются в единицах RPM (например, 3600 RPM), предупреждения об отказе отсутствуют.
- **Фактический результат:** Показание 3600 RPM, статус кулера нормальный.
- **Статус:** **Passed**

### Группа 3: Удаленный доступ (Remote Access)

#### TC 3.1: Подключение к серверу через IPMI
- **ID:** `TC-ACC-01`
- **Приоритет:** Blocker
- **Предусловие:** Сетевой порт BMC доступен, протокол IPMI-over-LAN включен.
- **Шаги выполнения:**
  1. Выполнить команду запроса информации о контроллере через защищенный протокол RMCP+:
     `ipmitool -I lanplus -H <BMC_IP> -U root -P 0penBmc bmc info`.
  2. Проверить код завершения утилиты и наличие информации о версии прошивки (`Firmware Revision`).
- **Ожидаемый результат:** Код возврата 0. Возвращается блок параметров BMC: Device ID, Firmware Revision (OpenBMC), IPMI Version 2.0.
- **Фактический результат:** Успешное подключение, получена версия микропрограммы BMC.
- **Статус:** **Passed**

#### TC 3.2: Подключение к серверу через Redfish API
- **ID:** `TC-ACC-02`
- **Приоритет:** Blocker
- **Предусловие:** Веб-сервер bmcweb / Redfish сервис запущен на порту 443/8080.
- **Шаги выполнения:**
  1. Отправить POST-запрос на создание сессии:
     `curl -k -i -X POST -H "Content-Type: application/json" -d '{"UserName":"root","Password":"0penBmc"}' https://<BMC_IP>/redfish/v1/SessionService/Sessions`.
  2. Проверить HTTP-код ответа сервера (200 OK или 201 Created).
  3. Проверить наличие токена сессии `X-Auth-Token` в заголовках ответа.
- **Ожидаемый результат:** HTTP-код 200/201. Заголовок `X-Auth-Token` содержит валидный токен безопасности сессии.
- **Фактический результат:** Код 200/201 получен, токен сессии успешно извлечен.
- **Статус:** **Passed**

### Группа 4: Логирование событий (Event Logging)

#### TC 4.1: Проверка записи логов при включении сервера
- **ID:** `TC-LOG-01`
- **Приоритет:** High
- **Предусловие:** Сервер выключен. Журнал событий доступен для чтения.
- **Шаги выполнения:**
  1. Очистить или зафиксировать текущий хвост логов SEL:
     `ipmitool -I lanplus -H <BMC_IP> -U root -P 0penBmc sel list`.
  2. Инициировать включение сервера (`power on`).
  3. Запросить обновленный журнал SEL или просмотреть вкладку Event Log в Web UI:
     `ipmitool -I lanplus -H <BMC_IP> -U root -P 0penBmc sel elist last 5`.
- **Ожидаемый результат:** В журнале событий появляется новая запись с временной меткой, категорией `Power Supply / Chassis` и описанием `Host power on / System Power State Changed to On`.
- **Фактический результат:** Запись о включении хоста зафиксирована в SEL с актуальным временем.
- **Статус:** **Passed**

#### TC 4.2: Проверка записи логов при ошибке
- **ID:** `TC-LOG-02`
- **Приоритет:** High
- **Предусловие:** Стенд готов к фиксации событий безопасности.
- **Шаги выполнения:**
  1. Выполнить серию некорректных попыток авторизации с неверным паролем через Web UI или Redfish API:
     `curl -k -X POST -d '{"UserName":"root","Password":"BadPassword"}' https://<BMC_IP>/redfish/v1/SessionService/Sessions`.
  2. Запросить журнал системных событий:
     `curl -k -u root:0penBmc https://<BMC_IP>/redfish/v1/Systems/system/LogServices/EventLog/Entries`.
  3. Проверить наличие сообщения об ошибке аутентификации со статусом `Warning` / `Critical`.
- **Ожидаемый результат:** В журнале фиксируется событие категории `Security / Authentication Failed` с указанием имени пользователя и предупреждением о нарушении безопасности.
- **Фактический результат:** Событие ошибки авторизации успешно сохранено в системном журнале.
- **Статус:** **Passed**
